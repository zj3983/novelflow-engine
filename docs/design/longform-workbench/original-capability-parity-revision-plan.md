# PR #45 原项目能力对齐整改计划

状态：PLANNED

适用 PR：#45 `feat: 长篇小说四页工作台与逐章创作闭环`

计划基线：`cee547820d02c9a2a6897d8ca19f87f002a115d1`

合入基线：`fd9fc354352d8c3355009e0c6ce89b789f904ed2`
目标：保留四页产品结构，同时恢复原项目中作者实际需要的能力，使新工作台成为现有小说工程的产品入口，而不是一套功能缩水的独立界面。

## 1. 整改结论

当前四页工作台已经复用了原项目、候选正文和确认服务，但页面能力没有完成对齐：

- **作品页**缺少作品详情、出版素材和完整的归档／回收管理。
- **全书规划页**把大量构建任务直接铺到页面上，同时隐藏了原有的分层大纲、伏笔和可编辑规划能力。
- **写作页**保留了主要候选闭环，但缺少章节搜索、复制和清晰的章节状态定位。
- **故事设定页**只从当前状态读取人物，导致角色不全；世界信息被压平成重复的正文摘录；人物稳定设定、当前状态、关系和未来计划没有清晰分开。
- 全局导航只暴露四页和设置，使仍未迁移的作者功能变得不可发现。

整改采用一条原则：**后端继续使用原有工程能力和数据权威，四页工作台通过产品映射完整呈现作者需要的功能。** 不在前端解释 Build Graph、artifact、revision、stale、preflight、provider 等内部概念，也不另建存储、模型路由或调度器。

## 2. 不可变约束

1. 四个主页面保持为：作品、全书规划、写作、故事设定；模型设置保留独立入口。
2. 只修改未确认候选正文。已确认正文可查看、搜索和定位，不在本轮加入历史改稿。
3. 每章必须人工确认；不得接入自动确认或连续自动发布。
4. Canon 硬冲突、规划采纳权威、候选来源复检、revision 校验和确认事务不得放松。
5. 模型调用保持在项目锁外；提交前重新核对源状态。
6. 不调用真实 provider，不修改受保护小说；测试使用合成项目和注入模型。
7. 原作者页面在能力完成迁移并通过验收前继续保留，不能先删路由或统一跳转。
8. 普通页面不得出现内部工程字段、原始诊断、原始 JSON 或完整私密正文。
9. 所有新增写操作必须复用现有服务和版本检查，不允许 React 直接拼装或推断工程状态。
10. 每项代码改动必须能对应本文的页面任务或验收场景。

## 3. 原能力迁移分类

### A. 必须迁入四页的作者能力

| 原能力 | 新入口 | 产品呈现方式 |
|---|---|---|
| 作品概览、章节数、字数、当前进度 | 作品 | 作品卡和作品详情 |
| 简介、封面生成或更新 | 作品 | “作品资料”操作区 |
| 归档、回收、恢复、导入 | 作品 | “管理作品”菜单和回收列表 |
| 总纲、分卷规划、章节规划 | 全书规划 | 全书方向、卷计划、近期章节三层结构 |
| 伏笔台账 | 故事设定 | “伏笔线索”标签页，并在规划页显示近期相关线索 |
| 章节搜索、定位、复制 | 写作 | 章节目录搜索和正文工具栏 |
| 人物档案、动态状态、关系 | 故事设定 | 人物卡、当前状态和关系区 |
| 世界背景、规则、地点、势力 | 故事设定 | 结构化世界设定，不重复铺正文摘录 |
| 已确认事实和来源 | 故事设定 | 只读事实，短依据和章节来源 |
| 作者硬要求和后续计划 | 故事设定 | 可编辑创作要求和未来计划 |

### B. 继续保留在内部或机器接口的工程能力

- Build Graph 任务、依赖和内部节点状态。
- artifact、revision、stale、validation_failed 等工程字段。
- 原始 diagnostics、capability、preflight、provider/protocol/model 元数据。
- 原始 prompt、技能管理、运行日志和调试数据。
- AI Public API、CLI/MCP 所需的机器结构。

这些能力不能通过“高级模式”重新暴露给普通作者。需要用户处理时，由后端转换为用户文案和可执行动作。

### C. 独立入口

- 模型配置继续使用 `/config`。
- 归档和回收属于作品管理，可在作品页进入独立子视图。
- 内部调试页面保留直达路由，但不进入普通导航。

## 4. 产品数据契约调整

当前通用 `PlanningPart` 和扁平 `StoryEntry` 不足以承载原项目能力。先在后端建立明确的产品投影，再改页面。

### 4.1 作品投影

新增或扩展：

- `BookLibraryItem`
  - 书名、类型、确认章节数、总字数、当前卷、最近更新时间。
  - 当前待办及一个主要动作：继续改稿、继续检查、确认本章、继续规划或开始写作。
  - 归档／回收状态。
- `BookDetails`
  - 故事简介、封面状态、目标篇幅、每章目标字数、作者要求摘要。
  - 当前规划和写作进度的用户文案。
  - 可用动作：编辑资料、生成简介、生成封面、归档、移入回收、恢复。

数据继续来自现有项目和出版素材服务。目标字数是创作目标，不映射为模型输出硬上限。

### 4.2 规划投影

以用户概念替换“遍历所有 Build Graph 任务”的做法：

- `PlanningView`
  - 全书方向、结局目标、当前卷、前文衔接、采纳状态。
  - `volumes`: 卷名、卷目标、主要冲突、人物变化、结尾转折、状态。
  - `upcoming_chapters`: 近期 3–12 章的目标、冲突、推进点和相关伏笔。
  - `author_reminders`: 本阶段必须遵守的作者要求。
  - 可执行动作：准备方向、生成／修复规划、保存可编辑字段、采纳当前规划、准备下一卷。

后端可以读取 Build Graph，但不能把节点和字段原样传给普通 Web。规划内容变化后，原采纳结果必须失效；已被正文消费的规划继续受保护。

### 4.3 写作投影

在现有候选闭环上补充：

- `ChapterDirectoryItem`: 章号、标题、确认／候选状态、当前选择、可定位标记。
- 章节目录搜索结果和匹配数量。
- 当前章的阅读／候选／检查／待确认状态文案。
- 正文复制动作；复制只发生在浏览器，不改变项目。
- 历史章节只读；候选允许手改、AI 修改和重新检查。

服务端确认继续校验候选正文、检查结果和源状态的一致性。前端按钮状态不能替代最终校验。

### 4.4 故事设定投影

- `CharacterView`
  - 完整人物名册，而不是只读取当前 state 中出现的人物。
  - 稳定档案、当前状态、已确认事实、人物关系、未来计划分别呈现。
  - 事实来源只使用可靠章节依据。
- `WorldSection`
  - 世界背景、规则、地点、势力等结构化分组和短摘要。
  - 不把完整正文或重复长摘录当作设定内容。
- `ForeshadowView`
  - 未回收／已回收筛选、首次出现、当前计划、相关章节、可编辑状态。
  - 保存时复用现有版本冲突检查。
- `AuthorRequirementsView`
  - 硬要求、篇幅目标和未来创作意图。

已确认事实为只读；本轮只允许编辑未来计划、作者要求和现有服务允许修改的结构化设定。

## 5. 分阶段实施

### 阶段 0：冻结对齐清单

**工作内容**

1. 将原路由中的作者功能逐项登记到“作品／规划／写作／故事设定”。
2. 为每项能力登记：读取来源、写入服务、权限或版本校验、目标页面、测试场景。
3. 标记只供内部使用的页面和字段，禁止它们进入普通导航。
4. 固定四张设计稿为视觉基准，记录桌面和窄屏主要布局。

**产物**

- 能力对齐矩阵。
- 页面和接口清单。
- 明确的“迁入／内部保留／独立入口”分类。

**完成门槛**

- 所有原作者能力均有去向，没有仅以“原路由仍可访问”作为迁移结果。
- 没有为了补齐页面而新增平行工程系统。

### 阶段 1：补齐后端产品投影

**主要文件**

- `apps/api/routes/longform_product.py`
- `packages/story_core/longform_presentation.py`
- `packages/story_core/product_presentation.py`
- 相关 Core/API 测试

**工作内容**

1. 增加作品详情与作品管理投影，复用现有出版素材和项目管理服务。
2. 用明确的全书、分卷和近期章节结构替换普通 Web 所用的泛化 `planningParts`。
3. 从完整角色来源构建人物名册，再合并当前状态、确认事实和未来计划。
4. 将世界设定按背景、规则、地点和势力聚合，删除重复的长正文摘录。
5. 将伏笔、关系、作者要求映射为独立产品结构。
6. 所有用户问题由服务端输出用户文案、依据和允许动作；Web 不解析内部枚举。
7. 写操作继续调用现有存储和服务，保留版本冲突、来源复检和项目锁边界。

**可观察结果**

- 合成项目的 4 名人物均出现在故事设定投影中。
- 规划接口只返回作者可理解的结构，不返回整套构建任务。
- 世界设定不包含重复无限正文摘录。
- 作品详情能够读取简介、封面、篇幅目标和管理状态。

**验证**

- Core 投影测试。
- API 契约测试。
- 版本冲突、事实只读、规划采纳失效和已消费规划保护测试。

### 阶段 2：逐页恢复产品能力

**主要文件**

- `apps/web/components/longform/Workspace.tsx`
- `apps/web/components/longform/product.ts`
- `apps/web/components/longform/live-adapter.ts`
- 工作台样式和页面专项测试

#### 2.1 作品页

1. 保留当前作品卡、继续入口、新建、导入和归档。
2. 增加作品详情抽屉或页面内详情区，展示简介、封面、章节数、字数、目标和当前进度。
3. 复用原有简介／封面服务，按钮使用“生成简介”“生成封面”等用户文案。
4. 补全归档、回收、恢复流程；破坏性动作保留清晰确认。
5. “继续写作”优先级保持：待确认候选 → 待完成规划 → 最近确认章节。

#### 2.2 全书规划页

1. 页面只展示全书方向、分卷目标、近期章节和前文衔接。
2. 删除按任务遍历生成的大段构建内容。
3. 恢复作者可修改的规划字段，并复用原有保存和采纳服务。
4. 将系统完成规划和作者采纳规划分开显示。
5. 在卷末提供“准备下一卷”，进入规划、调整、采纳后再生成候选。
6. 与当前规划相关的伏笔只做摘要和跳转，完整管理放在故事设定。

#### 2.3 写作页

1. 保留现有候选生成、手工改写、AI 修改、重新检查、确认和确认并继续。
2. 增加章节搜索；搜索只影响章节目录。
3. 点击章节时，仅在目标不在目录可视区时滚动目录，不移动正文阅读位置。
4. 增加复制当前章节正文的操作，不改变项目数据。
5. 清晰显示“正在生成／等待检查／等待确认／已确认／失败可重试”等用户状态。
6. 正文区域保持主要视觉空间，桌面端目标不少于内容区约 70%。
7. 历史章节只读，不增加自动连续生成或自动确认入口。

#### 2.4 故事设定页

1. 人物标签页显示完整人物名册，并区分稳定档案、当前状态、确认事实和未来计划。
2. 增加人物关系展示；关系使用用户语言和可追溯来源。
3. 世界规则标签页按背景、规则、地点、势力展示，不重复整段正文。
4. 伏笔线索标签页支持未回收／已回收筛选、来源定位和安全修改。
5. 创作要求标签页允许修改后续计划和作者要求。
6. 已确认事实明确只读；“发现前文矛盾”只定位相关章节并解释可处理范围。

**完成门槛**

- 阶段 0 中标记为“必须迁入”的能力都能从四页直接到达。
- 页面不存在仅为了调试而展示的工程状态或原始 JSON。
- 新页面操作经过真实本地 API 和注入模型，不使用前端伪成功状态。

### 阶段 3：导航与旧入口收敛

**主要文件**

- `apps/web/components/ws/WorkspaceShell.tsx`
- `apps/web/app/page.tsx`
- 相关路由和导航测试

**工作内容**

1. 普通导航保持四页和设置。
2. 在尚未完成能力迁移时，提供明确的用户语言临时入口；不得称为“高级模式”。
3. 完成对齐验收前，保留原 `/projects/[id]/*` 作者页面直达能力，便于回退和对照。
4. 只有当作者能力不再依赖旧路由才能被发现时，才允许把根入口稳定收敛到 `/workspace`。
5. 内部调试页面继续从普通导航隐藏，机器接口不受影响。

**完成门槛**

- 作者不用知道旧 URL，也能完成作品管理、规划、写作和设定操作。
- 旧直达路由继续可用，不因本轮删除造成不可恢复迁移。

### 阶段 4：稳定性与页面验收

**功能场景**

1. 新建小说 → 方向选择 → 规划采纳 → 第一章候选 → 人工确认。
2. 手工改稿和 AI 改稿 → 旧检查失效 → 重新检查 → 确认。
3. 硬冲突阻断，修改并通过检查后恢复确认。
4. 生成失败、检查失败、重启恢复、确认成功但下一章启动失败。
5. 双击、刷新、旧页面提交和规划漂移不造成重复写入或错误确认。
6. 卷末准备下一卷，保留前卷正文、事实和确认结果。
7. 作品归档、回收、恢复、导入；简介和封面操作使用注入后端。
8. 角色、关系、世界、伏笔和作者要求都能从新页面查看；可写范围符合约束。

**长程回归**

- 从新建项目开始，经实际 API 和注入模型逐章确认至少 60 章。
- 必须跨越 50 → 51 章，中途包含一次生成失败、一次检查失败和一次候选改稿。
- 不使用预填 50 章替代。
- 证明流程、幂等和数据保护，不宣称真实模型文本质量。

**页面验收**

- 桌面和约 390px 窄屏均可操作。
- 四页与固定设计稿逐页对比，记录偏差及处理结果。
- 目录滚动与正文滚动相互独立；编辑草稿和刷新恢复正常。
- 页面检查禁用词：`artifact`、`revision`、`stale`、`validation_failed`、`provenance`、`preflight`、`raw JSON`、`provider protocol` 及其直接内部枚举。
- 用户问题必须显示为：发生了什么、受影响内容、可执行动作。

**验证层次**

1. Core/API 定向测试。
2. Web 组件和页面专项测试。
3. 专用真实 FastAPI + 浏览器联调。
4. 构建和类型检查。
5. 最终 HEAD 的 Python/Web CI。

上述证据分别报告，任何一层不能替代另一层。

## 6. 文件责任边界

实施时按下列边界避免同一核心文件被多人同时修改：

| 责任区 | 核心文件 | 责任 |
|---|---|---|
| 产品投影 | `longform_presentation.py`、`product_presentation.py` | 完整角色、结构化规划／世界／伏笔、用户状态 |
| 产品 API | `longform_product.py` | 查询、动作映射、服务复用、版本和权限校验 |
| Web 数据层 | `product.ts`、`live-adapter.ts` | 产品 DTO、请求与错误映射，不解释工程字段 |
| 四页界面 | `Workspace.tsx` 及样式 | 页面结构、交互、响应式和可访问性 |
| 原能力对照 | 原 `/projects/[id]/*` 页面 | 只作为能力来源和回归基准，避免顺手重构 |
| 验收 | Core/API/Web/E2E 测试 | 真实调用链、页面流程、失败恢复和长程回归 |

若并行实施，同一表格行只有一个修改负责人；跨区变更通过明确接口交付后再集成。

## 10. 防跑偏判定

出现以下任一情况，应停止该项实现并回到本计划核对：

- 新增功能无法对应四页中的页面、动作或验收场景。
- 为展示一个状态而让前端解析内部工程字段。
- 复制原服务形成第二套存储、模型调用或调度流程。
- 用旧页面仍可访问来替代新页面的能力迁移。
- 页面外观通过，但实际 API 操作链未接通。
- API 测试通过，但浏览器无法完成同一操作。
- 长程回归通过，却没有验证页面或作者操作。
- 合成流程通过后宣称真实模型文本质量已经验收。

页面外观、作者操作链、后端能力和长程稳定性必须分别验收，任何一项不能替代另外三项。
