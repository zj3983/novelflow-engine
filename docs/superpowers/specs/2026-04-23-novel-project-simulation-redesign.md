# 小说项目演化引擎纠偏设计稿

## 1. 背景

当前项目最初参照 `MiroFish` 的核心思路启动：从种子材料出发，构建一个可持续演化的世界，再由多个智能体推动世界发展，最终将演化结果表现为可阅读内容。

现阶段实现已经具备基础多 Agent 编排、章节生成、状态回写和前端工作台，但产品中心对象和生成主链路发生了偏移：

- 首页主要展示 `story_id` 与章节记录，而不是一本小说项目
- 章节生成链路更像“直接写一章”，而不是“先推演世界，再将结果写成章节”
- 世界背景、关系变化、长期记忆仍是附属摘要，没有成为下一章的主驱动源
- 旧测试故事和污染数据会持续干扰用户对系统能力的判断

这导致产品看起来更像一个“多 Agent 包装的章节生成器”，而不是“小说世界演化引擎”。

本次设计的目标不是推翻现有基础，而是将产品中心重新拉回到 `MiroFish for Novel Simulation` 的方向：以“小说项目”和“世界演化”为核心，章节正文降级为演化结果的表现层。

## 2. 目标

### 2.1 核心目标

- 将系统主对象从 `Story` 升级为 `NovelProject`
- 将生成链路从“直接写章节”改为“推演优先，正文后出”
- 让首页成为“小说项目工作台”，而不是 `story_id` 列表页
- 让用户能直接看到 AI 的三层价值：世界推演、角色决策、小说表达
- 让新导入项目默认走新架构，旧故事退居兼容层

### 2.2 成功标准

- 用户打开首页时，看到的是小说项目名、当前世界状态和演化进度，而不是技术 ID
- 每次生成下一章前，系统先生成可解释的推演中间产物，再产出正文
- 章节历史能够显示“这一章为什么会这样发展”，而不只是正文文本
- 项目在重新导入或重建后，能够从干净状态开始推进，不复用旧污染状态
- 降级推演、接口失败、模型失败等异常不再伪装成正常生成结果

## 3. 非目标

- 本轮不追求一次性重写全部底层存储
- 本轮不引入复杂分布式 Agent 基础设施
- 本轮不做开放式多人协作编辑
- 本轮不实现完整知识图谱或外部图数据库
- 本轮不强制迁移所有旧故事数据为新项目结构

## 4. 核心设计原则

### 4.1 项目优先

用户面对的始终应该是“一本小说项目”，而不是一个内部生成记录。

### 4.2 世界优先

世界状态、关系变化、事件推进是主驱动；章节正文是这些变化的文学化输出。

### 4.3 推演优先

先决定这一轮世界发生了什么，再让 Writer 将其表现成章节内容。

### 4.4 可解释优先

前端必须能展示本轮推演理由，而不仅仅展示最终正文。

### 4.5 兼容优先

旧故事先兼容读取，不阻塞新项目走上正确结构。

## 5. 核心对象重构

### 5.1 NovelProject

`NovelProject` 是新的顶层对象，代表一本正在持续演化的小说项目。

建议字段：

- `project_id`
- `title`
- `source_path`
- `seed_outline`
- `world_summary`
- `author_constraints`
- `status`
- `active_branch_id`
- `created_at`
- `updated_at`

职责：

- 承载一本书的身份信息
- 关联导入源与约束信息
- 决定当前主分支
- 成为首页工作台的默认展示对象

### 5.2 StoryBranch

`StoryBranch` 表示某一条实际演化分支。分支不是顶层产品对象，而是项目内部的一种历史与探索能力。

建议字段：

- `branch_id`
- `project_id`
- `parent_branch_id`
- `branched_from_chapter`
- `current_chapter`
- `agent_settings`
- `simulation_state`
- `latest_world_state`
- `created_at`
- `updated_at`

职责：

- 保存一条连续演化路径
- 允许从历史章节处分叉
- 为章节时间线和分支切换提供支撑

### 5.3 WorldState

`WorldState` 是系统的核心驱动对象，不再只是摘要。

建议字段：

- `current_situation`
- `active_conflicts`
- `established_facts`
- `relationship_changes`
- `foreshadowing_state`
- `timeline`
- `current_focus`
- `risk_flags`

职责：

- 记录世界当前局势
- 为导演、角色、记忆三个推演层提供统一输入
- 在每章结束后被回写更新

### 5.4 ChapterOutput

章节正文从核心对象降级为结果快照。

建议字段：

- `chapter_number`
- `title`
- `body`
- `chapter_intent`
- `character_moves`
- `event_plan`
- `state_delta`
- `simulation_summary`
- `next_seed`
- `created_at`

职责：

- 存储这一轮推演的可阅读表现
- 保留中间推演痕迹，供前端展示和调试

## 6. 生成链路重构

新的章节循环固定拆成七步。

### 6.1 Project Context Assemble

从 `NovelProject + StoryBranch + WorldState` 组装当前上下文：

- 书名与项目身份
- 最近章节推进位置
- 当前世界局势
- 活跃角色与冲突
- 既有事实、伏笔与禁区

输出：`ProjectContext`

### 6.2 Director Simulation

导演代理负责决定本轮该推进什么，而不是直接写文。

输出内容：

- 本章主冲突
- 本章次冲突
- 当前焦点角色
- 节奏类型
- 是否允许新角色进入
- 本轮推进目标

输出：`ChapterIntent`

### 6.3 Character Evolution

角色代理根据长期目标、短期情绪、关系网络和最近事实，为每个关键角色计算行动倾向。

输出内容：

- 每个角色想做什么
- 角色是否会支持、阻碍或偏离主线
- 是否产生新角色候选

输出：`CharacterMoves[]`

### 6.4 Memory Enforcement

记忆代理提供硬约束，防止人物失忆、世界设定漂移和伏笔消失。

输出内容：

- 必须继承的事实
- 必须延续的关系变化
- 不可违背的设定约束
- 本轮需要保留或回收的伏笔

输出：`MemoryConstraints`

### 6.5 Simulation Merge

系统将导演意图、角色行动和记忆约束合并为真正的事件序列。

输出内容：

- 本章会发生哪些事件
- 事件先后顺序
- 哪些事件改变世界状态
- 哪些事件只影响人物关系
- 哪些事件埋下新伏笔

输出：`EventPlan`

### 6.6 Writer Rendering

写手代理只负责将 `EventPlan` 文学化。

约束：

- 不得擅自改写核心事件结果
- 不得突破导演与记忆层的限制
- 负责节奏、视角、语言风格、场景表现

输出：`ChapterOutput.body`

### 6.7 State Commit

章末必须完整回写：

- `WorldState`
- 角色目标变化
- 关系变化
- 活跃冲突
- 伏笔状态
- 下一章种子

输出：`StateDelta`

## 7. 新角色出现策略

系统必须支持“新角色在推演中自然出现”，但不能无约束膨胀。

规则如下：

- 新角色只能在 `Director Simulation` 允许的前提下进入正式世界状态
- `Character Evolution` 可以提出候选，不可直接落地为正式角色
- `Memory Enforcement` 负责校验是否与既有设定冲突
- `State Commit` 阶段才能将通过审核的新角色写入 `WorldState`

前端展示时，新角色分为：

- 候选角色
- 已引入角色
- 已冻结角色

## 8. 前端工作台重构

首页重构为“小说项目工作台”。

### 8.1 顶部项目条

显示：

- 小说名
- 项目状态
- 当前主分支章节进度
- 最近一次成功推演时间
- 主按钮：`继续推演下一章`
- 次按钮：`打开配置中心`

不再默认展示裸 `story_id`，技术 ID 只出现在调试信息或详情区。

### 8.2 左栏：项目资料

显示：

- 导入书稿目录
- 原始大纲
- 世界背景摘要
- 风格 / 禁区 / 硬约束
- 角色档案入口
- `从导入源重建项目` 按钮

### 8.3 中栏：当前演化主区

显示：

- 当前世界局势
- 本轮主冲突
- 当前焦点角色
- 最近一章摘要
- 下一轮演化种子
- 章节时间线

点击某章时，除了正文，还应显示：

- 本章意图
- 角色行动
- 事件推进
- 世界状态变化

### 8.4 右栏：状态侧脑

显示：

- 活跃角色
- 关系变化
- 伏笔与待回收项
- 风险提醒
- 最近一次推演日志

### 8.5 分支与旧故事展示

当前右侧裸 `story_id` 列表需要降级。

新规则：

- 默认展示“项目分支”，而不是“故事 ID 列表”
- 旧测试故事放入“历史记录 / 旧数据”
- 主界面不再铺满 `打开 s-xxxx`

## 9. 异常与降级策略

异常不能再伪装成正常生成。

### 9.1 允许的降级

- 模型临时失败时，可使用最近稳定 `WorldState` 继续做有限推演
- 某一层 Agent 失败时，可由更保守的默认策略代替该层

### 9.2 禁止的行为

- 直接返回像真正文一样的 mock 文本却不提示
- 前端无法区分完整推演与降级推演
- 在失败情况下静默覆写世界状态

### 9.3 前端提示

页面必须明确展示：

- 本轮是否完整推演成功
- 哪一层失败
- 是否启用了降级策略
- 当前结果是否建议用户采用

## 10. 数据兼容与迁移策略

本轮不强制重写历史数据，但要明确分层。

### 10.1 新数据

- 新导入一律创建 `NovelProject`
- 新项目默认走新工作流

### 10.2 旧数据

- 旧 `Story` 记录继续可读
- 旧数据默认归入“历史记录 / 旧数据”
- 旧数据不再作为首页主入口

### 10.3 重建能力

必须提供 `从导入源重建项目`：

- 清理污染状态
- 重新提炼项目上下文
- 从干净世界状态重启主分支

## 11. 实施边界

建议拆成三个连续阶段：

### 阶段一：项目实体化

- 引入 `NovelProject`
- 首页标题与对象改为项目
- 旧故事降级为兼容层

### 阶段二：推演链路落地

- 实现 `ChapterIntent / CharacterMoves / MemoryConstraints / EventPlan`
- 调整生成流程为推演优先
- 保存中间产物

### 阶段三：工作台与解释性呈现

- 工作台改成项目视角
- 展示中间推演层
- 完成异常与降级可视化

## 12. 测试策略

### 12.1 数据层

- 新建项目时应正确生成 `NovelProject`
- 新分支应正确挂到项目下
- 旧故事应仍能读取

### 12.2 推演层

- Director 输出必须先于 Writer 执行
- Character 输出不能绕过 Memory 约束
- State Commit 后世界状态必须与章节结果一致

### 12.3 前端层

- 首页默认显示项目名而不是技术 ID
- 点击章节能看到正文与推演解释
- 异常状态有明确提示
- 历史旧故事不会污染主入口

### 12.4 回归层

- 导入书稿后能成功创建项目
- 重新生成第一章时不会复用旧污染正文
- 配置页保存的模型配置仍会正确应用到新项目

## 13. 预期结果

本轮改造完成后，产品应该被用户感知为：

- 一个以小说项目为中心的创作与演化工作台
- 一个先进行世界推演、再生成章节正文的多 Agent 引擎
- 一个可以让角色在世界背景下自然发展，而不是被动拼接剧情的系统

届时，AI 的价值不再只是“帮忙写章节”，而是成为“推动小说世界持续演化的核心引擎”。
