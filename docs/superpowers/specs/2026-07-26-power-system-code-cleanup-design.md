# Power System Code Cleanup Design

## Goal

Clean up the recently added novel-type and power-system code without changing product behavior. The result should make normalization, validation, prompt projection, templates, and one-off migration responsibilities easy to locate and test independently.

## Scope

This cleanup covers:

- `packages/story_core/power_systems.py`
- `packages/story_core/power_system_templates.py`
- `packages/story_core/writing_packet.py` only where it consumes power-system data
- `scripts/upgrade_project_power_system.py`
- directly related tests

It does not cover the general orchestration pipeline, project-store decomposition, UI redesign, prompt rewriting, schema changes, or novel data changes.

## Architecture

### Public compatibility facade

`packages/story_core/power_systems.py` remains the stable import location. Existing public names and call signatures stay available there, so API routes, world enrichment, writing packets, scripts, and tests do not need a coordinated migration.

The facade delegates to two focused internal modules:

- Power-system specification module: canonical fields, bounded normalization, completeness validation, and validation errors.
- Power-system prompt module: legacy summary rendering, sensitive-value redaction, progression slicing, and prompt-budget fitting.

The prompt module consumes normalized data through the specification module. The specification module must not depend on prompt rendering.

### Templates

`power_system_templates.py` remains responsible for built-in novel-type templates, defensive copies, and compact template views. It must not validate project instances or render writing prompts.

### Writing packet

`writing_packet.py` remains a consumer. It extracts the protagonist's current progression hints and asks the public power-system facade for the relevant prompt slice. It must not duplicate normalization, validation, or template rules.

### Migration

The migration script keeps filesystem containment checks, backup handling, transactional writes, and command-line behavior. Its fixed `p-gou-webgame-restored` power-system payload moves into a separate migration-data module so that operational code is not mixed with several hundred lines of project content.

The migration remains intentionally restricted to the same target project. This cleanup does not turn it into a general migration framework.

## Data Flow

1. A novel type supplies a copied and compacted power-system template.
2. Project world data is normalized and validated against that template.
3. The writing pipeline extracts current level and path hints from character state.
4. The public facade returns a bounded prompt slice containing only relevant progression data.
5. The migration script builds its project payload, validates it through the same public facade, then writes it transactionally.

No stage may silently repair invalid project data beyond the existing normalization behavior.

## Compatibility Requirements

The cleanup must preserve:

- Public function names, arguments, return shapes, and exceptions from `power_systems.py`.
- JSON field names and ordering where tests or persisted output depend on them.
- Validation rules and error messages.
- Legacy-summary redaction behavior.
- Prompt-slice content, selection order, and size limits.
- Novel-type template values and compact representation.
- Migration command arguments, target-project restriction, backup behavior, and generated bytes.
- Existing UI and API behavior.

No project files or generated chapters are modified by this work.

## Error Handling

Validation errors continue to use `PowerSystemValidationError`. Invalid or hostile mapping-like values remain bounded and rejected according to current behavior. Migration path violations and transaction failures retain their existing exception types and rollback behavior.

Internal modules do not introduce new fallback paths. The public facade is the only compatibility boundary.

## Testing

Before moving implementation, add characterization tests for:

- Import compatibility through `packages.story_core.power_systems`.
- Equivalent normalization, validation, summary, and prompt-slice outputs.
- Migration payload equivalence after extraction.

Then run the focused power-system, novel-type, writing-packet, world-context, enrichment, and migration tests. Run the broader story-core and API suites if the focused set passes.

## Completion Criteria

The cleanup is complete when:

- Each module has one documented responsibility.
- Existing callers continue to import the same public API.
- No power-system business rule is duplicated in writing-packet or migration orchestration code.
- Characterization and existing tests pass without updating expected product output.
- Git contains no generated project-data changes or unrelated formatting churn.
