# 自然对话链路设计

## 目标

让不同题材的正文对话更接近现代中文交流习惯，允许人物解释半句、犹豫、回避、闲话和不完全有效的回应。先用现有写作流程解决，不增加对话 Agent，不增加模型调用。

## 根因

当前对话要求分散在角色上下文、写手规则、任务书和审稿中。部分规则要求完整口语，另一些规则要求每句话都推进信息、压缩表达、减少解释。规划字段中的目标、情绪和动作又会被拼成摘要式文字交给写手，最终容易形成电报句、各说各话和借人物之口说明设定。

## 方案

### 对话场景合同

`dialogue_context.py` 只整理场景级信息：

- 对话为什么发生。
- 参与者各自想得到什么。
- 双方关系和语气边界。
- 当前主要情绪。
- 哪件事不能直接说破。
- 对话结束后，情绪、关系、信息或行动中的哪一项发生变化。

合同不生成台词，不把 `goal`、`emotion`、`action` 拼成压缩句，也不包含题材术语。

### 通用写手

通用写手只保留三条对话原则：

1. 人物先接住上一句话，再表达自己的意思。
2. 根据关系和场合决定称呼、语气与能说到什么程度。
3. 允许停顿、解释、回避和闲话；整场对话产生变化即可，不要求每句都交付新信息。

网游称呼、交易习惯和职业术语继续由网游题材模块提供，不进入通用提示词。

### 审稿

确定性审稿只拦截：

- 连续省略对象或因果的电报句。
- 相邻台词互不回应。
- 把系统规则、后台标签或提纲说明直接写成台词。

审稿返回问题类型和修改方向，不附固定改写范例，避免模型照抄。正常的紧急短句、迟疑、闲话和稍长回答不得误判。

## 数据流

章节规划提供人物行动与冲突 -> 对话上下文整理成场景合同 -> 通用写手读取合同并写完整交流 -> 题材模块补充行业语言 -> 综合审稿检查三类硬问题 -> 必要时进入现有的一轮定向修订。

## 兼容性

- 不修改章节、角色卡和项目存储格式。
- 不增加 Agent、接口或生成阶段。
- 保留现有 `dialogue_context` 字段读取兼容，迁移后不再向新提示词输出废弃字段。
- 已有题材模块继续按当前注册机制工作。

## 测试

- 对话合同包含关系、目的、情绪边界和预期变化，但不产生台词或压缩摘要。
- 写手提示词不再要求每句都推进新信息，也不出现网游专用内容。
- 审稿能识别连续电报句、答非所问和台词说明设定。
- 审稿允许紧急短句、自然迟疑、解释半句和日常过渡。
- 运行写手提示词、现代中文对话、题材隔离和完整生成测试。

## 暂不实施

不增加对话 Agent。只有在这套链路经过实际章节生成后仍不能稳定改善，才评估单独的对话修订模型调用。
