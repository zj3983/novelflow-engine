# 商业爽文写作 Skill 设计

## 目标

将用户提供的网文爽文方法整理为可安装、可选择、可叠加的本地 Skill 包。它不是小说题材，也不修改现有题材模板；新书可在网游、玄幻、仙侠、都市、科幻等题材之上选择启用。

实现后应满足：

- 旧项目默认不启用，现有《万界维修工：从家电到仙器》不受影响。
- 新建小说时可以在“叙事增强”中选择“商业爽文推进”。
- 爽文方法分别进入总纲、阶段大纲、章节细纲、正文和审稿，不把整包内容一次性塞给写手。
- 保留具体步骤、正例、反例和题材示例，不压缩成抽象口号。
- 审稿只给报告，不自动重写正文。
- 不引入“能断句就断句”“所有人倒吸凉气”等会制造短句和套路腔的硬规则。

## 非目标

- 不把“爽文”加入小说类型列表。
- 不自动给旧项目启用。
- 不重写现有章节。
- 不把所有爽文都限定为打脸、反派羞辱或一击秒杀。
- 不恢复模型自动改稿。

## 选择的架构

新增独立 Skill 包 `commercial-shuangwen`，而不是继续扩充 `chinese-webnovel-skills` 中已有的单一 `shuangdian` 模块。

原因：

- 现有 `shuangdian` 主要描述打脸四拍，范围偏窄。
- 独立包可以在项目中整体启用，也可以单独控制子模块。
- 题材与叙事方法保持分层，爽文可以与任意题材叠加。
- 后续可用同样方式增加经营、幕后流、悬疑推进等叙事增强包。

目录结构：

```text
data/skill-packs/commercial-shuangwen/
├── manifest.json
├── SKILL.md
└── skills/
    ├── plot-engine/SKILL.md
    ├── chapter-sop/SKILL.md
    ├── writer-execution/SKILL.md
    ├── review-checklist/SKILL.md
    └── genre-examples/SKILL.md
```

## 模块职责

### 1. `plot-engine`

服务于总纲和阶段大纲，尽量还原“5—15章大循环”。每个循环必须产出：

1. 主角需求：需要什么、为什么现在需要、失败会失去什么。
2. 压力来源：人物、组织、规则、危机或时间限制怎样造成实际损害。
3. 信息差：主角和读者知道什么，对手误判了什么。
4. 反击方式：使用哪项已存在的能力、资源、证据或布局。
5. 具体回报：实力、资源、身份、关系或现实处境怎样变化。
6. 后续牵引：本轮结果引出哪个更大的问题。

保留原方法中的“设局/需求、打压/拉仇恨、降维打击、震惊与收割”，但将绝对要求改成可执行约束：

- 压力必须具体，不要求每轮都由傲慢反派制造。
- 反击必须有前文依据，不允许临时爆种。
- 碾压可以是能力、规则、信息或资源上的优势，不要求每次一击秒杀。
- 他人反应只选择有身份和立场的人，不写整齐划一的围观震惊。

### 2. `chapter-sop`

服务于章节细纲，保留“起、承、转、合”的具体写法，但不强制固定百分比。

- 起：第一场承接上一章尚未完成的具体事件，不复述上章摘要。
- 承：给出至少一项明确反馈，如物品、能力、钱、线索、关系或身份变化。
- 转：已有计划遇到来自既有人物、规则或伏笔的变化，并产生代价或选择。
- 合：用具体事件收尾，明确下一章能接着处理什么。

每章细纲增加机器可读字段：

```json
{
  "payoff": {
    "need": "",
    "pressure": "",
    "hidden_advantage": "",
    "concrete_reward": ""
  },
  "chapter_sop": {
    "opening_carry": "",
    "mid_feedback": "",
    "turn": "",
    "ending_hook": ""
  }
}
```

这些字段必须填写成当前故事中的人物、地点、物品和行动，不允许使用“制造爽点”“形成反转”等后台标签代替剧情。

### 3. `writer-execution`

只服务于正文写手，内容保持短而具体：

- 写清对手为什么会作出错误判断，不能把对手写成无缘无故犯蠢。
- 反击时写清使用了什么能力、条件、证据或信息。
- 收获落到具体结果，不用作者总结“主角变强了”。
- 主角的强大通过行动结果和少量有立场的人物反应表现。
- 心理可以写，但必须依附当时的动作和处境。
- 对话按现代中文把意思说完整，不为了气势省略主语、对象、原因和结果。
- 正文不出现“爽点、情绪释放、信息差、降维打击、收割”等工作流词。

明确排除：

- “能断句就断句，能回车就回车”。
- 固定使用“瞳孔收缩、倒吸凉气、喉结滚动、冷汗浸透”。
- 所有角色都用同一种震惊反应。
- 主角在正文中解释自己为什么厉害。

### 4. `review-checklist`

服务于人工触发的审稿，检查：

- 本章目标是否明确。
- 压力是否造成实际影响。
- 信息差是否清楚且没有破坏既定视角。
- 对手的误判是否合理。
- 主角反击是否使用已存在的底牌。
- 是否兑现具体回报。
- 他人反应是否重复、夸张或模板化。
- 章末是否留下可直接承接的具体事件。
- 是否出现空洞震惊、强行反派、凭空危机、工作流词或短句装腔。

审稿产物进入报告，不触发自动重写。没有实际执行该检查时，页面显示“尚未执行爽文检查”，不能显示虚假的零问题通过。

### 5. `genre-examples`

保存网游、玄幻、仙侠、都市和科幻的完整示例。运行时先读取项目题材，只提取对应题材内容。

每个题材至少提供：

- 一个5—15章循环示例。
- 一个信息差反击示例。
- 一个章节细纲示例。
- 一个章末钩子正反例。
- 一个动作与心理正反例。

结构示例用于学习因果关系，禁止照抄人物名、道具名和句子。

## 示例保留与提取

现有 `extract_skill_instructions` 会跳过标题中含“示例”和“反例”的章节。需要改为支持显式示例块，而不是全局过滤。

Skill Markdown 使用以下标题：

```markdown
## 规则
## 正例
## 反例
## 结构示例
```

提取器按调用阶段返回：

- 大纲：规则 + 一条结构示例 + 当前题材循环示例。
- 细纲：规则 + 一条章节示例 + 一组章末正反例。
- 写手：规则 + 一组与当前任务最相关的正反例。
- 审稿：检查清单 + 一组正反对照。

每个 Skill 包仍受字符预算限制。例子按完整块截取，不允许从中间截断。

## 阶段路由

扩展 Skill purpose，使模块可以显式声明：

- `outline`
- `chapter_plan`
- `writer`
- `reviewer`
- `genre_examples`

不再只依赖文件名和简介猜用途。`manifest.json` 或模块 frontmatter 可声明 `purposes`，加载器解析后写入模块摘要。

调用关系：

```text
开书总纲生成
  -> outline + genre_examples

阶段大纲生成/扩展
  -> outline + genre_examples

滚动章节细纲
  -> chapter_plan + genre_examples

正文写手
  -> writer + 本章细纲产物

人工审稿
  -> reviewer + 正文
```

写手不直接读取 `plot-engine` 的全文，只读取细纲已经落地的本章需求、压力、底牌、反馈和钩子。

## 新书界面

在开书页面的小说类型之后增加“叙事增强”，与题材分开：

```text
小说类型：玄幻
核心设定：万物维修
叙事增强：商业爽文推进
行文风格：轻松幽默
```

行为：

- 默认不选择任何叙事增强。
- 选择“商业爽文推进”时，新项目保存 `commercial-shuangwen` 到 `enabled_skill_ids`，并保存该包需要的模块键到 `enabled_skill_module_ids`。
- 不修改旧项目配置。
- 项目创建后仍可在 Skill 页面逐个关闭子模块。

## 数据流

1. 用户在开书页面选择题材和叙事增强。
2. 项目保存题材插件与 Skill 选择，两者互不覆盖。
3. 各阶段按 purpose 读取已启用模块。
4. `genre-examples` 根据题材插件选择示例，不匹配的题材示例不进入上下文。
5. 大纲阶段把爽文结构落到正式大纲字段。
6. 细纲阶段把结构变成本章具体事件。
7. 写手只拿本章计划、写作执行规则和少量例子。
8. 审稿只生成报告，由用户决定是否重写或扩写。

## 错误处理

- Skill 包缺失：项目仍可生成，页面提示该叙事增强未安装。
- 子模块未启用：对应阶段不读取，不回退为全包加载。
- 项目题材无法识别：只加载通用示例，不猜测网游或仙侠。
- 例子超过预算：保留完整规则，减少例子数量，不截断例子。
- 爽文检查未执行：显示“尚未执行”，不能以空数组表示通过。

## 兼容性

- 保留现有 `shuangdian` 文件，避免破坏已经引用它的项目。
- 新项目优先使用独立的 `commercial-shuangwen` 包。
- 旧项目的 `enabled_skill_ids` 和 `enabled_skill_module_ids` 不迁移、不自动变更。
- 通用题材模板、网游题材模板和写手基础提示词不加入爽文专属规则。

## 测试要求

### Skill 加载

- 可以加载独立包和五个子模块。
- 显式 purposes 正确解析。
- 未启用模块不进入上下文。
- 正例、反例和结构示例按完整块提取。

### 阶段隔离

- 总纲只读取 `outline` 和对应题材示例。
- 细纲读取 `chapter_plan`，并生成具体字段。
- 写手不读取宏观 Skill 全文。
- 审稿模块不进入正文提示词。

### 题材适配

- 网游项目只加载网游示例。
- 玄幻项目只加载玄幻示例。
- 未识别题材只加载通用示例。

### 项目行为

- 新书不选择增强时 `enabled_skill_ids` 为空。
- 选择商业爽文后保存正确的包和模块。
- 旧项目配置保持不变。
- 《万界维修工：从家电到仙器》不被自动启用。

### 审稿行为

- 未运行爽文审稿时显示“尚未执行”。
- 审稿结果只保存报告，不修改正文。

## 验收标准

- 可以新建一本玄幻或网游小说并选择“商业爽文推进”。
- 总纲中能看到具体的阶段需求、压力、信息差、反击和回报。
- 章节细纲能看到承接、反馈、变化和具体章末事件。
- 写作包只包含本章所需爽文规则和少量对应题材例子。
- 正文不出现工作流术语，也不会因该 Skill 产生大量残缺短句。
- 未启用该 Skill 的项目生成上下文与行为保持不变。

## 可选的受保护项目校验

默认集成测试只使用临时哨兵目录。需要额外确认某个既有项目不会被测试修改时，必须显式设置环境变量，路径不写入源码或测试数据：

```powershell
$env:NOVEL_AUTOGROWTH_PROTECTED_PROJECT_ROOT = '<existing-project-root>'
python -m pytest tests/story_core/test_commercial_shuangwen_skill.py::test_integration_commercial_shuangwen_http_workflow_isolates_creation_and_manual_review -q
Remove-Item Env:NOVEL_AUTOGROWTH_PROTECTED_PROJECT_ROOT
```

测试会在运行前后计算该目录的内容指纹；任何变化都会使测试失败。另有单元测试确认只有显式设置的目录会被选为受保护根目录。
